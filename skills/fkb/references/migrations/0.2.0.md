# 0.2.0 - a bundle can be shared with other people, live

**What changed.** Filing used to end at a commit: the concept was saved on this machine and
getting it to anybody else was a git command somebody had to remember. A bundle may now say
which branch it is shared on, and `fkb sync` carries commits to and from that branch as part
of filing - out after a note is written, in before the bundles are read. Nothing changes for
a bundle that does not say it, which is every bundle on this machine today.

This is a new capability, not a breakage. Every existing manifest is already correct.

**What to do.**

1. **Ask whether any of their writable bundles is one other people also write into.** Run
   `fkb list` and go through the writable ones with them. The question is not "is it on a
   forge" - a private bundle can have a remote and still be theirs alone. It is whether
   somebody else commits into it. If the answer is no for all of them, say so and go to
   step 5.

2. **Find out which branch that bundle is shared on.** Do not guess and do not default to
   `staging`: pushing a concept onto a branch somebody uses for something else is the one
   outcome this field exists to prevent. If the repository has a protected default branch and
   a long-lived branch everybody works on, the second is the answer. If it has neither yet,
   the shape to set up first is in
   [bundle infrastructure](../bundle-infrastructure.md#sharing-a-bundle-with-several-people) -
   read that with them before writing the field.

3. **Add `sync: <branch>` to that bundle's entry** in `$XDG_CONFIG_HOME/fkb/workspace.yaml`,
   beside `writable: true`. It is only valid on a writable bundle: `fkb` refuses a manifest
   that puts it on a sealed one, on load, rather than at the first push.

   ```yaml
   team:
     path: /home/you/knowledge/team
     referenceable_by: [private]
     writable: true
     sync: staging
   ```

4. **Put the checkout on that branch and check it works.** `fkb lint <bundle>` warns when the
   checkout has drifted onto another branch, and `fkb sync <bundle> --check` says what a real
   run would do and changes nothing. Run the second one and read it back to them. A bundle
   added from now on can skip all of this: `fkb add <name> --clone <url> --writable --sync
   <branch>` writes the field and checks the branch out.

5. **Say what filing does from now on**, in one line, whether or not anything was shared: a
   bundle with a `sync` branch is pushed after a concept is filed into it and pulled before it
   is read, and a bundle without one behaves exactly as it always has - committed, never
   pushed.

**If they decline.** Nothing happens and nothing breaks. A bundle with no `sync` branch is
committed to and never pushed, which is what every bundle did before this release. The field
can be added the day it becomes true; there is no cost to leaving it out, and a bundle that
is not actually shared should not have it.

**How to tell it worked.** `fkb list` shows a `sync` line for every bundle - `null` for the
ones nobody shares, the branch name for the one that is. For that one, `fkb sync --check`
names the remote branch it would push to rather than refusing.

**One thing to warn them about.** `fkb sync` refuses far more often than it acts: a
half-written file in the tree, a checkout on another branch, a rebase in progress, a conflict.
Every refusal keeps their commits and says what to do, and none of them is a failure of the
filing that produced the commit. There is no flag that overrides any of it.
